# zk-noai-zh

中文文本去 AI 化的 Agent Skill。给 Agent 装上以后，它知道**按什么顺序**把一段"一看就是 AI 写的"中文改成"像人写的"，也知道**每步做完什么样算合格**。

不是提示词模板，是一套带执行流程、检查清单和可运行脚本的工作手册。

---

## 这个项目能干什么

### 它治什么病

AI 写的中文有三个层次的毛病，很多人只盯着第二个：

**第一层，格式与符号。** 这是最显眼、也最容易被机器检测到的一层：

- Markdown 残留：正文里冒出 `**加粗**`、`- 列表项`、`## 标题`、` ```代码块``` `、`> 引用`
- 中英之间整齐划一的空格：AI 喜欢在"AI 技术"中间加空格，真人往往忽加忽不加
- 段落长度过于均匀：每段都三到四行，读起来像印刷表格
- 空行规律：段与段之间永远空一行，从不例外
- 标点频率均匀：破折号、省略号用得又对又密

**第二层，内容与表达。** 这层更隐蔽，靠正则抓不住：

- 套话模板：`随着……的不断发展`、`综上所述`、`在当今……的背景下`
- 书面翻译腔：`进行了一个……的过程`、`呈现出……的特征`、`具有一定的……性`
- 逻辑台阶：`首先……其次……再次……最后`、`基于上述分析`
- 举例教科书化：动不动就是苹果、特斯拉、华为、星巴克
- 没有个人印记：通篇正确的废话，看不到"我"
- 前后不一致：前面说"三个原因"后面列了四个，同一数据出现两个值

**第三层，文件元数据。** 正文之外还藏着东西，打开文件看不出来，但随手一查就露：

- **生成器指纹**：`dc:creator` 写着 `python-docx`，`Application` 写着 `Microsoft Macintosh Word`——不是真实来源，冒充环境
- **假时间戳**：`created` / `modified` 停在 `2013-12-23T23:15:00Z`，这是 python-docx 模板写死的默认值，成百上千份文档共用同一秒
- **统计值异常**：`Words` / `Characters` / `Pages` 全是 0，写满几千字的文档不可能没统计
- **隐藏二进制部件**：`docProps/thumbnail.jpeg`，里面可能是别处的页面截图
- **`customXml` 里的残留数据**：可能是参考文献库（要留），也可能是别处粘过来的脏数据（要清）

这一类最容易被忽略，因为它不影响阅读——你打开文件看正文，一切正常。但把它传出去的那一刻，作者、生成工具、编辑时长、原始模板全都跟着走了。

本项目的核心判断是：**先做完第一层，再动第二层，元数据放到最后统一清。** 格式没清干净就去调语气，等于白费功夫；元数据提前清了，后面每保存一次就全回来。

### 它处理什么文件

| 类型 | 正文改写 | 元数据清洗 | 隐形字符 |
|---|---|---|---|
| 纯文本 / Markdown | ✅ | — | ✅ |
| `.docx` | ✅ | ✅ | ✅ |
| `.xlsx` | 只清单元格填充词 | ✅ | ✅ |
| `.pptx` | ✅ | ✅ | ✅ |
| `.pdf` | ❌ 见「已知边界」 | ⚠️ 待实现 | ⚠️ |

### 元数据清洗实测

拿一份 python-docx 生成的 Word 文档跑一遍，清洗前后对比：

| 字段 | 清洗前 | 清洗后 |
|---|---|---|
| `dc:creator` | `python-docx` | 空 |
| `dc:description` | `generated by python-docx` | 空 |
| `Application` | `Microsoft Macintosh Word` | 空 |
| `dcterms:created` | `2013-12-23T23:15:00Z` | 当前时间 |
| `dcterms:modified` | `2013-12-23T23:15:00Z` | 当前时间 |

**改动范围极小。** 同一份文件共 17 个 zip 部件（Word 文档本质就是个 zip 包），清洗只动了 `docProps/core.xml` 和 `docProps/app.xml` 两个。正文 `word/document.xml`（77412 B）、样式表、编号、字体表、主题——逐字节比对完全一致。段落数、汉字数、表格行列数全部不变。

**默认保留 `customXml`。** Word 的参考文献库存在这里，删了会丢书目数据。只有当它确实是空壳时才清。确实要连数据一起删，用 `--drop-customxml`。`thumbnail.jpeg` 这类二进制部件默认不动，需要单独处理。

### 它不干什么

- **不做"过检测"。** 目标是自己看完顺眼，不是为了骗过某个检测器
- **不保证改写后的文本更好。** 它只负责减掉机器味，内容质量还是你的事
- **不会悄悄改动数据。** 发现前后矛盾或无法核实的数据时，`verify` 会单列出来报警，而不是自动"修正"
- **不会伪造来源。** 元数据清洗是把机器痕迹清空，不是编一个假作者填上去

## 怎么实现的

整体思路：**能用确定性脚本判断的，绝不用模型；必须用模型的，用脚本兜底检查。**

原因很简单：改写文本的是模型，跑去检查它的也是同一个模型、同一套偏好。让它自我审查，检出率接近零。所以校验环节必须由脚本做，且脚本只信可以被算出来的东西。

### 四层结构

```
第 0 层  确定性守卫      脚本        不可绕过
第 1 层  7 轮改写流程    Agent 按手册执行
第 2 层  回归校验        脚本        改写完必须过
第 3 层  元数据清洗      脚本        所有改动落盘之后才做
```

### 第 0 层：确定性守卫

| 动作 | 命令 | 做什么 |
|---|---|---|
| 冻结 | `freeze` | 算出原文 SHA256 并存档，后续校验都以它为准 |
| 体检 | `report` | 一次给出：隐身字符指纹 + 中文 AI 特征分 + 文档元数据 |
| 清字符 | `layer-a` | 零宽字符、BOM、word joiner、NBSP、双向控制符 |

**为什么要冻结哈希：** 改写完成后如果忘了原文早就被覆盖，`verify` 就变成了拿新文件跟新文件比，永远通过。哈希这一环是整个防线的地基。

**为什么先清字符：** 零宽字符会干扰后面的正则匹配（一句"综上所述"中间夹一个 U+200B，词表就匹配不上），而且它是元数据里最直接的机器痕迹。

### 第 1 层：7 轮改写流程

| 轮次 | 做什么 | 判据 |
|---|---|---|
| 1 | Markdown 清理 | 正文里不该出现 `**` `` ` `` `>` `-` `1.` `#` |
| 2 | 套话清理 | 开头结尾的模板句全部删掉，不替换成别的套话 |
| 3 | 段落节奏 | 长段拆短、短段合并、空行打乱规律 |
| 4 | 个人印记 | 按文体加"我觉得""这里有意思的是"，正式文书可一个不加 |
| 5 | **前后一致** | 术语、数据、论点数量全文自洽 |
| 6 | 可控的不完美 | 句式参差、口语插入语；错别字默认关闭 |
| 7 | 全文默读 | 找剩下卡壳的地方 |

**第 5 轮是硬约束，没有例外。** 一致性不通过，其他六轮做得多好都不算完成。这一条是刻意跟"自然度"打架的：宁可保留一句看起来不够自然的重复措辞，也不能让同一个概念有两种叫法。

**第 6 轮为什么不鼓励写错别字。** 原始清单里有"加入少量不完美"，本仓库保留这一轮但改了实现方式：优先用句式参差、口语插入语制造呼吸感。理由——AI 痕迹是"读起来像机器"，错别字是"看起来不专业"，用后者换前者通常不划算。

**文体豁免。** 同一套规则套到公文上是灾难。`SKILL.md` 里给了一张表，公文/学术论文/工作汇报/随笔各有各的收紧或放宽项。

### 第 2 层：回归校验

`verify` 做四项确定性比对，全是硬门槛，任何一项不过就整体失败：

| 检查项 | 门槛 | 防的是什么 |
|---|---|---|
| 原文哈希 | 必须与冻结值一致 | 拿旧报告验新文件 |
| 特征分 | 改写后不得上升 | 越改越像 AI |
| 专名与数字 | 零丢失 | 悄悄删掉"EGFR-TKI"或"85%" |
| 汉字数 | 删减不超过 25% | 把正文删没了 |

第三项是关键。改写着为了让文本"自然"，很容易顺手把看起来啰嗦的专业名词和数字删掉——这类损失肉眼极难发现，但一次就能让整篇事实失真。

### 第 3 层：元数据清洗

文档正文改完、校验也过了，才轮到它。`meta` 做的是把文件属性里的机器痕迹清空：

| 处理 | 字段 |
|---|---|
| 清空 | `dc:creator`（作者）、`dc:description`（说明）、`cp:lastModifiedBy`（最后修改者）、`Application`（应用程序）、`AppVersion` |
| 改写 | `dcterms:created` / `dcterms:modified` 的模板默认值，改成当前时间 |
| 保留 | `customXml`（Word 参考文献库，删了会丢书目）、`docProps/thumbnail.jpeg`、`cp:revision`、`TotalTime` |

**为什么不直接重建一个干净文件。** 重建要把正文重新写一遍，样式、编号、域代码、表格、批注全都有丢的风险。`meta_docx.py` 直接改 zip 里的 XML，只碰 `docProps/` 两个部件，其余字节原样不动——上面「元数据清洗实测」那张表就是这个做法的证据。

**这一层不能提前。** `python-docx` 每次 `save()` 都会重新生成 `docProps/`，先清完再保存一次，清掉的痕迹会原样回来。同理也不能放在 `verify` 之前——它会改动文件字节，哈希比对就失去意义了。

## 使用流程

### 完整流水线

```bash
# 0. 冻结原文
python scripts/deai.py freeze 文档.docx

# 1. 体检：隐身字符 + AI 特征分 + 元数据
python scripts/deai.py report 文档.docx

# 2. 清隐形字符
python scripts/deai.py layer-a 文本.txt --clean -o 净.txt

# 3. 逐条看命中的 AI 特征词，确认哪些是真问题
python scripts/deai.py score 文本.txt --explain

# 4. 按 SKILL.md 的 7 轮流程改写（这一步由 Agent 做）

# 5. 回归校验：四项硬门槛
python scripts/deai.py verify --original 原.docx --revised 改后.docx

# 6. 元数据清洗——必须最后做
python scripts/deai.py meta 改后.docx --clean -o 净.docx
```

### 顺序为什么不能变

**元数据必须放在所有内容改动之后。** `python-docx` 每次调用 `save()` 都会重新生成 `docProps/`，先清完再保存一次，清掉的痕迹会原样回来。

**校验必须放在元数据之前。** 元数据清洗会改动文件字节，跑在 `verify` 前面会让哈希比对失去意义。

### 单体命令

不想跑完整流水线时，各子命令可以单独用：

| 命令 | 场景 |
|---|---|
| `report` | 只想知道这篇有多像 AI、文件里藏了什么 |
| `score --explain` | 只想看具体命中了哪些特征词、出现在哪句 |
| `meta --clean` | 只想清掉 Word 文档属性里的作者、生成器、假时间戳 |
| `layer-a` | 只处理从网页/PDF 复制过来带零宽字符的文本 |

## 中文打分器为什么要自己写

上游的 `score_stylometry.py` 规则全是为英文设计的，对中文基本失效。同一段 446 字的中文 AI 腔文本，上游给出：

```
word_count=33        实际 413 个汉字
sentence_count=1     实际 9 句
ai_ngram_density=0.0 matched_markers=[]
score=0.0077  tier=low
```

根因在源码里：

- `RE_WORDS = re.compile(r"\b[\w'-]+\b", re.UNICODE)` —— 对无空格的中文，整段只切出一个 token
- 切句正则 `(?<=[.!?])\s+|\n+` —— 根本不认 `。！？`
- `AI_PHRASE_PATTERNS` 60 余条全是 `delve into` / `a testament to` / `rich tapestry` 这类英文套话

本仓库重写后同一段文本得 **0.9112 / high**。中文规则按"字当量"切词，按 `。！？；…` 切句，特征词分 9 组、权重 0.4–1.5，并新增段落长度 CV —— 中文 AI 最稳定的特征是**每段长度过于接近**，而不是句长。

**刻意不收录**"核心""关键""重要""问题""影响""实现""提升"这类词。它们在真实专业文本里是实义词，收了只会制造误报。

## 安装

复制整个目录到 Agent 的 skills 目录即可。以 DSH 为例：

```
%APPDATA%\dsh-desktop\harness\skills\zk-noai-zh\
```

目录内需包含 `SKILL.md`、`references/`、`scripts/`。

脚本只依赖 Python 3 标准库，无需 pip 安装任何东西。Windows 下建议先设：

```powershell
$env:PYTHONIOENCODING = "utf-8"
```

否则中文输出会乱码。

## 已知边界

- **pdf 只做元数据，不改正文。** 重排正文要吃中文字体子集，会留下字体回退、字距不匀、行尾溢出，视觉损伤大于 AI 味本身。要改文字请找回源文件重导出
- **pdf 元数据清洗暂未实现**，本机 Python 环境没有 pikepdf / PyMuPDF
- **Excel 不做句子级改写**，只做元数据清洗 + 纯文本单元格删填充词
- **打分器对少于 120 汉字的样本返回 `uncalibrated`**，短文本没有统计意义
- **低分 ≠ 没问题。** 实测一篇 4836 字的医学综述只有 0.135 分，但里面仍有 18 段真实毛病（"需要说明的是"×5、破折号×8）。照命中词去改，别盯着总分刷分
